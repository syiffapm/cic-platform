1. Summary

The front-end prototype runs every portal on data kept in the browser. For production, that logic moves into 25 backend engines behind one API gateway. Each engine owns its data, exposes versioned APIs, and writes every sensitive action to the audit store. Portals never talk to a database directly.

One core, many portals. Registry, inquiry, disputes and billing are built once and reused by every portal.
Security enforced on the server. Tenant, role, CRUD permission and data scope are checked by the permission decision point on every call.
Maker-checker everywhere. Licence changes, corrections, rule activation, publishing, role changes and large loans go through one approval engine.
Evidence by design. Hash-chained audit, consent references, rule versions and data dates travel with every report.
Bilingual. Content and UI strings are served in English and Myanmar (Unicode) from the CMS.
Integrations as options. NRC, MCIX, MMCB and alternative data sit behind an integration hub with their own agreements.

Phase legend

Pilot needed before the 5-MFI pilot · Production needed before scaling to 30 MFIs · Option after the foundation is stable, subject to agreements.

E02

Identity & Access Management (IAM)

PilotC1, SEC-01/02/07, ADM-03/04

Two identity realms — citizens and workforce — plus the permission decision point used by every service.

Scope

  • Citizen realm: registration with NRC + phone + own password, identity verification (selfie eKYC / SMS to phone on record at an MFI / branch activation code), SMS OTP on every sign-in, lockout after 5 failures
  • Workforce realm: CIC, Central Bank and MFI staff; SSO (OIDC/SAML) + TOTP/FIDO2; IP allow-lists; session policy 10 min idle / 8 h absolute
  • Policy decision point: role catalogue, CRUD + Approve + Export matrix per feature, data scope (all / regional / own institution / aggregates / masked PII)
  • Role builder and user assignment with maker-checker; MFI role templates assigned by MFI administrators
  • Dormant-account auto-disable (90 days), access recertification campaigns, break-glass accounts

E07

Inquiry & Credit Report Engine

PilotC6, MFI-02..06, PUB-09, AC05

Purpose-bound, consented inquiries that produce Basic/Full reports, PDFs and verifiable snapshots.

Scope

  • Search by NRC or CIC borrower ID; purpose code and consent reference mandatory
  • Report assembly: Basic (summary, exposure, delinquency flag, grade) and Full (24-month grid, guarantees, inquiries, dispute flags, reason codes)
  • Entitlement check: report unlocked per institution per borrower for 30 days (pay-per-report) or covered by subscription
  • Citizen personal report snapshots (issued after CIC approval, valid 30 days)
  • PDF rendering with QR, watermark, rule version and data date; public verification (valid / revoked / expired / not found)
  • Inquiry log that feeds "Who viewed my report"

E08

Scoring & Rules Engine

PilotC6, ADM-08, GOV-08/09/19, S4

Versioned rule sets for credit grade, early-warning and over-indebtedness — the same result everywhere.

Scope

  • Credit grade A–E with points and reason codes (no-hit returns no grade, never a low score)
  • EWS rules library (PAR30, late submissions, concentration…) generating alerts
  • Over-indebtedness rules (≥ 3 active loans, debt-to-income thresholds) by township
  • Rule-set lifecycle: draft → test on sample → approve → activate with effective date → rollback
  • Policy impact simulation on historical data; statistical score model as a later option

7. How the engines work together

Citizen gets a credit report

  1. PUB/BOR → E02 register, verify identity (eKYC or SMS), confirmation by E16
  2. BOR → E11 request report → E04 + E06 automated validation
  3. ADM officer → E11 approve (E17 rules) → E07 issue snapshot → E21 PDF + QR
  4. E16 SMS/email "report ready" → BOR views report; E19 logs every step
  5. Anyone → PUB → E07 verify report ID + code

Citizen applies for a loan

  1. BOR → E10 application + E09 digital consent
  2. MFI → E10 inbox → E07 inquiry (E15 charges Basic/Full or subscription; E08 grade)
  3. MFI → E10 decision (second approval via E17 above threshold) → disburse
  4. E10 → E04 posts the loan; E16 notifies the citizen; E20 updates lending statistics

Monthly data submission

  1. MFI system → E01 → E05 batch (idempotent) → validation report
  2. MFI checker → E17 sign-off with attestation
  3. E05 → E06 identity resolution → E04 load + reconciliation
  4. E08 EWS evaluation → E13 alerts; E20 KPIs; E19 audit

Dispute and correction

  1. BOR (or E14 helpdesk) → E12 dispute + evidence (E21 virus scan)
  2. MFI → E12 response / correction within SLA
  3. ADM steward → E12 approve (E17) → E04 new record version
  4. E16 notifies the citizen; SLA breach → E13 consumer-protection escalation

Publishing a public notice

  1. ADM editor → E18 draft (EN/MM) → E17 review by publisher
  2. E18 publish (classification enforced) → CDN / E22 search index
  3. Regulator notices: GOV → E18 → publication approval → PUB
